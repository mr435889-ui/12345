# Итоги анализа оптимальных интервалов между звонками

**Период данных:** 01.01.2024 – 01.09.2026  
**Источник прогона:** собственный SQL-скрипт (пересобранное ядро + отчёты)  
**Файл с агрегатами:** `Анализ`  
**Каналы:** Входящий и Исходящий — **всегда раздельно**

---

## 1. Цель и рамка ответа

По ТЗ на первом этапе нужно:

1. Проверить ключевые гипотезы (влияние МК, целесообразность сегментации).
2. Понять, чем заменить фиксированный интервал **2 часа**.
3. Сформировать основу для матрицы сегментов: **попытка × канал × (при необходимости) предыдущий исход / МК**.

**Что этот документ даёт:**  
исторические кандидаты интервалов и выводы по сегментации.

---



## 2. Формат выполненных работ



### 2.1. Что предоставили аналитики данных

По ТЗ «алгоритм определения оптимальных интервалов между звонками» отдел аналитики данных подготовил:

- SQL-скрипт построения витрины звонков / интервалов;
- агрегаты по квартильным группам интервалов;
- разрезы по номеру попытки и МК;
- выбор «оптимальной» группы по доле успешных соединений.

Каркас отчётности (квартили → группы → доля успеха → лучшая группа) **сохранён** и использован как базовый контур.

### 2.2. Почему ядро пересобрали на своей стороне

При проверке скрипта и логики связок выявлено:


| Проблема                                                                                              | Риск                                                                       |
| ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Связка звонков преимущественно через `interaction → contact` без надёжного добора по `payload.taskId` | Потеря / искажение звонков задачи                                          |
| Неоднозначная привязка результата звонка                                                              | Неверный «успех» на попытке                                                |
| Смешение интервалов внутри дня и через сутки                                                          | Искажение «рабочего» интервала перезвона                                   |
| Нет учёта предыдущего исхода                                                                          | Одна рекомендация для разных сценариев (недозвон vs «перезвонить позднее») |
| Спорное / неполное определение успеха на исходящем (в т.ч. `NULL`)                                    | Занижение/завышение доли успеха                                            |


Пока ядро ненадёжно, агрегаты сверху выглядят убедительно, но для решений по настройкам интервалов недостаточны.

### 2.3. Что изменено / добавлено (логика клиентов сохранена по согласованной воронке)

1. **Витрина звонков:** путь по `taskId` + добор по интеракции, дедупликация по `call_id` (приоритет источника).
2. **Результат звонка:** связка по паре interaction + call (с дедупом при дублях `call_id`).
3. **Успех:** успешное соединение по правилам анализа; на **исходящем** отсутствие результата (`NULL`) трактуется как недозвон.
4. **Интервалы:** в аналитику отчётов берутся только интервалы **внутри календарного дня** и `> 0`.
5. **Предыдущий результат звонка:** поля + отдельные срезы / отчёты R1–R5.
6. **Каналы:** сравнение и рекомендации только с разделением **Входящий / Исходящий**.
7. **Производительность:** материализация шагов во временные таблицы с индексами; прогон за ~2,5 года выполнен за приемлемое время.

Базовые таблицы 1–7 (контур АД) пересчитаны на новой витрине; поверх добавлен redial-контур по предыдущему исходу.

---



## 3. Правила чтения цифр

1. **Успех** = успешное соединение (не проект / не продажа).
2. **Квартильные группы** считаются внутри сегмента → «Группа 1» на исходящем **не равна** «Группе 1» на входящем по часам.
3. Сравнивать группы нужно **внутри канала** (и при redial — внутри среза предыдущего исхода).
4. Кандидат ≠ обязательная настройка в прод: это лучшая группа по истории при текущих правилах набора.
5. Таблица «Распределение по номерам попыток» **без канала** для выводов не использовать.

**Выводы:**

- «Короткий» интервал на входящем часто измеряется **минутами**; на исходящем в G1 для ранних попыток — **десятки минут / около часа**.



### 5.2. Кандидаты из готовых «оптимальных» отчётов

**Исходящий** (сводный отчёт «Оптимальные интервалы для Исходящего канала»):


| Попытка | Лучшая группа | Успешность | Медиана интервала     |
| ------- | ------------- | ---------- | --------------------- |
| 2       | Группа 1      | 23,12%     | **~71 мин** (1,176 ч) |
| 3       | Группа 1      | 23,39%     | ~75 мин               |
| 4       | Группа 1      | 30,78%     | ~36 мин               |
| 5       | Группа 1      | 33,03%     | ~44 мин               |
| 6       | Группа 1      | 34,43%     | ~38 мин               |
| 7–10    | Группа 1      | ~37–39%    | ~30–33 мин            |


**Входящий** (отчёт по МК × попыткам):

- У большинства МК и попыток лучшая группа тоже **Группа 1**.
- У крупных МК медианы G1 часто **1–5 минут** (иногда доли минуты).
- Это ближе к паттерну «быстрый перезвон», а не к дефолту 2 часа.
- Отдельные МК на части попыток выбирают G2/G4 — сегментацию по МК на входящем имеет смысл смотреть точечно, но базовый сигнал канала: **короткие интервалы**.



### 5.3. Как интерпретировать «Группу 1»

1. Квартили считаются **внутри** канала/сегмента — абсолютные часы разные.
2. На входящем короткий G1 может отражать текущую практику операторов, а не «идеальный» норматив для автонастроек.
3. На исходящем G1 ближе к «перезвону в пределах ~0,5–1,5 ч», а не к 2 часам по умолчанию — особенно на попытках 4+.

## 7. Ответы на гипотезы ТЗ (по текущим данным)



### Гипотеза 1. Влияние МК

- **Частично подтверждается как «смотреть внутри канала».**  
- На входящем по отчёту оптимальных групп есть МК, где на части попыток лучшая не G1.
- На исходящем объём сильно неоднороден по МК; детальные R3A/R3B показывают разброс, но **базовый каналный сигнал** (G1 + учёт prev-исхода) устойчивее, чем «уникальный интервал на каждую МК без проверки n».
- **Рекомендация этапа 1:**  
  - обязательная ось: **канал**;  
  - для исходящего — ещё **предыдущий исход**;  
  - МК — второй уровень (только при достаточном n, иначе fallback).



### Общая целесообразность отказа от фиксированных 2 часов

- Да, как исследовательский вывод: фиксированные 2 часа **не соответствуют** наблюдаемым лучшим группам.
- На входящем фактические лучшие интервалы существенно короче.
- На исходящем после недозвона кандидат ближе к **~0,5–1,5 ч** (зависит от попытки), после «перезвонить позднее» — к **~0,5–0,7 ч**, при заметно более высоком успехе.

## 8. Черновик матрицы-кандидата (не прод)



### 8.1. Входящий канал


| Ось                | Кандидат                                                                                       |
| ------------------ | ---------------------------------------------------------------------------------------------- |
| Попытки 2–8 (база) | Группа 1; ориентир — **короткий** интервал (минуты / низкая доля часа), не 2 часа              |
| МК                 | Точечно сверять крупные МК; при малом n — общий каналный кандидат / fallback                   |
| Предыдущий исход   | Учитывать как минимум на уровне мониторинга (R1); при внедрении — желательно отдельные правила |




### 8.2. Исходящий канал


| Предыдущий исход      | Попытка | Кандидат группы | Ориентир медианы (из R4)                         |
| --------------------- | ------- | --------------- | ------------------------------------------------ |
| Недозвон / NULL       | 2–3     | Группа 1        | ~1,5 ч                                           |
| Недозвон / NULL       | 4+      | Группа 1        | ~0,5–0,8 ч                                       |
| «Перезвонить позднее» | 2–10    | Группа 1        | ~0,5–0,7 ч                                       |
| Прочие                | —       | мало данных     | fallback / не строить отдельную сетку без добора |


**Fallback (как в ТЗ):** при `n` ниже порога (< 30 в ячейке) — безопасный дефолт (сейчас 2 ч или согласованное значение), статус данных = «недостаточно статистики».
